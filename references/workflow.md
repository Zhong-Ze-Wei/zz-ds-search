# 研究工作流

研究类任务才需要读这篇。简单的单次搜索请直接看 SKILL.md。

## 一、规划就是你的事

你是唯一的规划者。用你自己的语言能力拆解问题，直接调用本包的 Search / Fetch。不要调用 DeepSeek 聊天模型，不要建向量库，不要套固定主题模板。

在上下文里维护一份可核验的工作记录（复杂任务可展示给用户）：

- 原始问题与限制条件
- 待回答的子问题清单
- 计划查询及各自的目的
- 已读来源与对应证据（URL + 片段 + 检索日期）
- 剩余缺口 / 冲突
- 已用 Search / Fetch 次数

不保存隐式思维过程，只保留计划和证据。

### 拆查询的几条经验

- **长输入**：保留全部约束，拆成每条 ≤128 字符的查询。不要丢掉排除条件、时间、地区、版本。
- **陌生词**：先用原词探索，读完结果再展开，不要先编造定义和关联实体。
- **歧义**：不同解释会显著改变研究范围时澄清一次，或明确列出分支，不要无声选一个意思。
- **扩展维度**：别名、译名、组成部分、用途、限制、机制、时间变化、对照项、原始出处——只选与本次意图相关的。
- **反证**：不要只查支持预设观点的词。争议核实用中性问题，主动找可能推翻当前结论的证据。

## 二、小批次 + 动态补搜

先跑 1–3 个互补查询，读完再决定。标记每个子问题：

| 状态 | 含义 |
|---|---|
| supported | 已读到的证据直接支持 |
| partial | 部分支持，还差关键条件 |
| missing | 没有可用证据 |
| conflicting | 多个来源互相矛盾 |

supported 必须对应实际读到的证据，不是“有一个结果”。指出新增了什么信息、哪个缺口最影响答案，再选下一条查询或 Fetch。可以提前结束，不必用满预算。

### 停止条件（满足任一即停）

1. 主要问题已有足够证据，且影响结论的冲突已处理
2. 连续两轮没有有效新增信息
3. 预算用尽

因为第 2、3 条停止时，必须保留并说明关键缺口。

### 空结果

空结果不是失败，也不是“不存在”。可以修正一次检索表述，不要反复重试同一查询。

## 三、相关性与来源质量

语义筛选由你完成：

- 是否回答本次子问题
- 主体是否正确
- 时间 / 版本 / 地区是否符合
- 是否只是引流标题
- 正文是否有可引用信息

剔除重要材料时给一个具体理由。不要只因为关键词缺失、authority 分数低、或是论坛/媒体就删掉或采信——一份真实的问题记录可能比泛泛介绍更相关。

**来源优先级的通用原则：**

- 技术问题：官方文档、原始论文、源码、维护者的问题记录
- 其他主题：真正拥有该事实的机构、当事人、原始数据或同期记录
- 不同域名可能转载同一稿件；同一官网的不同页面也可能各有价值，核对署名和引文来源
- source_family_count 只是机械分组，**不证明信源独立**

## 四、读正文才算取得证据

Search 返回的 snippet / summary 是检索信号，不是原文。关键论断要么用 --need-content，要么单独 fetch。

Fetch 后必须核对标题、主体和关键段落。**HTTP 200 且正文非空，可能只是首页或导航页**——这时该次请求已消耗预算，但没有获得所需证据，要如实区分。

| 路线 | 含义 | 证据强度 |
|---|---|---|
| deepseek_api + content | 经 DeepSeek Fetch / need_content 得到的正文 | 高 |
| deepseek_api + summary/snippet | 只有检索摘要 | 中，需正文复核 |
| direct_fetch (open) | 直连兜底，不经 DeepSeek | 中，措辞需回原文确认 |

## 五、事实冲突核对

对要写进答案的关键事实，建立一张对照表：

**主体 — 属性/事件 — 值 — 适用条件 — 时间/版本/单位 — 证据 URL/段落**

不同条件可以同时成立。先对齐单位、时间、版本、地区和事件含义，再判断是否真矛盾。区分事实、评价和推测。

保留双方的最小证据片段，追溯原始材料或同期记录。**不能按多数票、来源分数、模型自信或单个名站裁决。** 足以判断时说明依据；不能判断时并列分歧或降低精度。

**没检测到冲突不等于核实成功。**

## 六、合并多轮结果

如果保存了多批 JSON：

~~~bash
python3 <skill_dir>/scripts/zz_ds.py merge "原始问题" round1.json round2.json
~~~

merge 不联网、不需要 Key，保留上游未完成状态（upstream_complete）和重复版本证据（alternates[].variant）。最多 8 个文件、400 条来源。

**merge 的 ok 只表示合并成功，不表示研究完成。**

## 七、重复页面里可能有矛盾

脚本默认会合并同 URL 和近似复制的页面，但会保留差异版本：

- duplicate 记录里的 reason 说明合并理由
- alternates[].variant 保存有差异的标题/摘要/正文
- changed_numbers 为 true 说明两份正文数字不同

**影响结论的版本必须逐个查看。** 近似复制的判定是保守的：数字顺序或否定词不同就不合并。

## 八、写答案

围绕用户原始问题组织，引用紧邻事实，注明检索日期和必要缺口。

- 简短结论 → 带来源的证据 → 不确定性
- 每个论断紧跟 URL
- 不要把“找到 N 条链接”当完成
- 不要为凑篇幅塞旁支信息
- 冲突无法解决就并列，不要选边

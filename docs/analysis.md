## 二、它做对了什么（原样保留）

1. 脚本不做语义判断。去重只做机械规则，相关性和冲突交回模型。
2. 空结果不是失败。ok 和 empty 同时为真，不计费不重试。
3. 错误码分离。401 / 402 / 403 / 404 各自独立，不糊成没查到。
4. 重定向即断链。绝不让 Bearer 流向重定向目标。
5. 错误体不回显。HTTPError 先 close 再处理。
6. 凭据安全。TTY 隐藏输入、700/600、原子写、拒软链、env 优先。
7. 重复保留证据。alternates 里的 variant 存差异版本，数字或否定词不同就不合并。
8. 不确定性写进数据。date 可为 null 但不伪造；source_family_count 明说不代表独立。
9. 响应硬校验。16 MiB 上限、schema 不符报错而不是静默当空。

## 四、产品逻辑的三次演进

### 第一版判断：自己用，砍掉 80%

分发给陌生人的合规成本（免责字段、三套自证、兼容层）对个人使用是纯负债。

### 第二版判断：分发后分层，不是加回来

分发场景里，同一个模块价值完全翻转：

| 模块 | 自己用 | 分发用 |
|---|---|---|
| 凭据安全 | 过度设计 | 必须 |
| 错误码分离 | 可有可无 | 必须 |
| 免责 JSON 字段 | 噪音 | 换成 confidence 加 gaps |
| 人物正则 | 负债 | 仍是负债，更该砍 |
| 预算自觉记账 | 无所谓 | 必须改 |

核心：自己用时复杂的成本你付；分发时复杂是给陌生人的信任押金。不增加总量，重新分配预算。

### 第三版判断：默认入口加软预算

最终选择默认搜索入口而非补充搜索，这个定位直接决定了预算必须软：

- 硬拦截会伤害默认入口的可用性
- 用户看到次数和行为提醒，就足够防住钱包意外
- 次数和提醒每次都可见，用户随时可停

## 五、最终改了什么

| 上游 | 本项目 | 原因 |
|---|---|---|
| 预算自觉记账 | 跨调用累计加 advisory 加 reset，不拦截 | 默认入口硬拦体验代价更大 |
| 只有 fetch | 增加 open 直连兜底 | 读文档跳外链不必每次付费 |
| 人物正则适配器 | 删除 | 中文耦合历史化石 |
| facts 和 conflicts | 删除 | 脚本做语义判断是过度承诺 |
| SKILL.md 69 行全塞 | 68 行入口加 references 按需 | 每次加载都交 context 税 |
| manifest 加 interface 加 reports | README 加 release 检查表 | 维护成本大于收益 |
| Python 3.10+ | 3.9+ | 实测可跑 |
| 无迁移 | 自动迁移 qiaomu 旧凭据 | 老用户零摩擦 |

## 六、验证

- 39 个单元测试全绿（凭据、重试、去重、合并、软预算）
- open 直连实测官方文档页，正文 9.6 KB 正确清洗
- search 用无效 Key 实测返回 401 且不泄露 Key
- 官方文档实测校对：修正了 QPS（Search 100、Fetch 25，上游记录的 5 已过时）和 HTML 实体解码两个问题

## 七、仍然不做什么

- 不做事实核查：只保证来源可追溯，不保证结论正确
- 不做跨提供商抽象：目前只接 DeepSeek，加抽象层是为没出现的需求付成本
- 不做硬预算拦截：违背默认入口定位
